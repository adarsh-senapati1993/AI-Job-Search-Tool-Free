## 1. Global Infrastructure & Tech Stack

This is a **100% Client-Side React SPA (Single Page Application)**. NO backend. NO database. NO server-side logic. The browser is the orchestration server.

### 1.1 Core Dependencies (`package.json`)
*   **Vite (`^5.1.0`)**: Build tool and dev server.
*   **React 18 (`^18.2.0`)**: UI Library.
*   **Tailwind CSS (`^3.4.1`)**: Utility-first styling (`dark:` class toggles, Glassmorphism).
*   **Zustand (`^5.0.11`)**: Global state management.
*   **p-limit (`^7.3.0`)**: **CRITICAL**. Throttles concurrent `Promise.all` loops for free-tier LLM API protection.
*   **pdfjs-dist (`3.11.174`)**: Client-side PDF parsing.
*   **tesseract.js (`^7.0.0`)**: Client-side OCR for images.

### 1.2 Global State Architecture (`lib/store.ts` & `lib/storage.ts`)
The app relies entirely on `LocalStorage` to mimic a database. Zustand manages the active runtime state and hydrates from Storage.

**Zustand Store (`AppStore`)**:
```typescript
type AppState = 'loading' | 'setup' | 'config' | 'dashboard';

interface AppStore {
    appState: AppState;
    activeProvider: string;          // 'perplexity', 'gemini', 'openai', 'anthropic'

    serperKey: string;
    userConfig: CandidateProfile | null;
    darkMode: boolean;

    // State mutators omitted for brevity

```

**LocalStorage Schema (`STORAGE_KEYS`)**:
*   `jobradar_user_config`: The `CandidateProfile` JSON.
*   `jobradar_latest_run`: `{ timestamp: number, leads: ScoredLead[] }`. Restores the active feed upon refresh.
*   `jobradar_lead_score_cache`: `Record<string, { url: string, profileHash: string, lead: ScoredLead }>`. Prevents re-analyzing the exact same job URL if the user hasn't changed their profile configuration (calculated via `computeProfileHash`).
*   `jobradar_seen_jobs`: String array of visited URLs (for styling visited links).

## 3. The Central AI Layer (`lib/*.ts`)

### 3.1 LLM Router (`lib/llm.ts`) & Providers
Acts as a proxy switchboard. Looks at `ACTIVE_LLM_PROVIDER` and routes the prompt payload to `gemini.ts`, `openai.ts`, or `anthropic.ts`. 

### 3.2 Resilience: `safeJSONParse` (`lib/api-utils.ts`)
LLMs hallucinate JSON blocks with markdown backticks `` `json ` `` or trailing commas. The system relies on a central regex extractor `extractJSONString` that scans the string, counts curly brace balances `{` vs `}`, and isolates valid JSON boundaries before executing `JSON.parse()`.

## 4. The Discovery Engine (`lib/discovery.ts`)

This is the raw data extraction pipeline. It is not an RSS feed. It is an algorithmic sniper.

### 4.1 Query Builder (`buildSearchQueries`)
Rejects monolithic Dorks (no massive `OR` strings).
1.  **Lookback Conversion**: Maps `14d` config to a raw timestamp used as a fallback.
2.  **Chunking**: Break `target_roles` into chunks of 4 MAX.
3.  **Atomic Target Generation**: Output arrays of targeted Search Queries:
    *   **ATS Direct**: `site:boards.greenhouse.io OR site:jobs.lever.co OR site:jobs.ashbyhq.com ("Role 1" OR "Role 2") "Location" ("remote" OR "work from home") -intitle:resume`.
    *   **LinkedIn Web**: `site:linkedin.com/jobs/view ("Role")`.
    *   **Regional Satellites**: Dynamically appends `site:naukri.com` if `india` is found in the Locations array.
4.  **Google Jobs API Grid**: The algorithm forces an exact string template: `User Role + jobs in + User Location` (e.g., `Product Manager jobs in New York`).

### 4.2 Serper API Payload & Chronological Override (`lib/serper.ts`)
To search "Past 7 Days", earlier versions used the messy `after:2024-03-01` text append. This is structurally flawed. The app now routes chronological settings exclusively to the native Google `tbs` parameter.

```typescript
// Serper API Payload (Direct Execution)
const body = JSON.stringify({
    q: query,
    page: page || 1,
    num: 20,
    tbs: tbsValue // e.g., "qdr:w" for past week, "qdr:d" for 24h
});
```

### 4.3 Deduplication & Bouncers (`lib/discovery.ts`)
Data returns as a noisy array of `RawSignal`s. The Bouncer loop:
1.  **Sanitization (`cleanSnippet`)**: `.replace(/skip to main content|we use cookies/gi, '')`. Strips HTML navbar pollution.
2.  **Spam Bouncer (`GLOBAL_SPAM_BLOCKLIST`)**: Hard drop on `['turing.com', 'bairesdev', 'cybercoders', 'canonical']`.
3.  **Semantic Gatekeeper (`passesRoleGuard`)**: Ensures the title contains at least one exact string match with Target Roles.
    *   *Leadership Bypass Hack*: If the user inputs "Head" or "VP", the guard allows non-exact synonyms like "Director" and "Principal" to pass through.
4.  **Canonical Normalization (`normalizeCompanyName`)**: Strips `Inc`, `LLC`, `Corp`.
5.  **Fingerprinting (`generateFingerprint`)**: Hashing formula: `FUZZY_V3:{NormalizedCompany}:{StrippedTitle}:{ContextHash}`. If an "Indeed" link and a "Greenhouse" link share this hash, `getSourceAuthority(url)` executes a tiebreaker to keep the high-fidelity ATS link.

## 5. The "Ruthless" Scoring Engine (`lib/scoring.ts`)

This represents the AI mathematical gatekeeper.

### 5.1 Concurrency Architecture
*   Wrapped strictly in `pLimit(5)` to dodge free-tier `429` Rate Limits from Gemini/OpenAI.
*   Every promise incorporates a `.catch()` block returning a "Fallback Lead" (Score: 25, Decision: REVIEW) instead of throwing an unhandled rejection that would crash the pipeline.

### 5.2 The Exact Prompt Constraints (DO NOT ALTER)
The prompt forces the LLM to behave like a ruthless technical recruiter calculating deductions:
```text
STRICT GATEKEEPING RULES:
1. ROLE MISMATCH HANDLING:
   - Use Candidate's Seniority Level to judge matches (+/- 1 level tolerance).
   - Soft mismatch (close but not exact): apply -10 penalty to match_score.
   - Hard mismatch: set is_role_match = false.

2. LOCATION MISMATCH HANDLING:
   - CRITICAL: If LOCATION says 'Unknown', INFER job location from company name or URL domain (.de = Germany).
   - Target vs Job Location Mismatch: apply -15 penalty.
   - If location STILL unknown after inference, cap location_fit at MAX 15/20.

3. WORK MODE RULES:
   - User wants "remote": Onsite/In-office → apply penalty (-20).
   - User has remote_base_country (e.g. India): "Remote - US only" → apply penalty (-20).
   - User wants "hybrid": Mismatch → apply penalty (-15).

4. MINIMUM SCORE GUARANTEE:
   - Do NOT give score of 0 unless complete spam. For mismatches, give low score (10-30).
```

## 6. UI Component Hierarchy & Render Lifecycle (`components/DiscoveryFeed.tsx`)

### 6.1 The Engine Room Rendering Phase
The UI relies entirely on masking asynchronous loading states to improve perceived performance.
1.  **"SEARCHING CLUSTERS" (Blank Feed)**: For 15 seconds, `searchForSignals` executes. The UI maps `searchProgress.found` to screen but displays 0 job cards.
2.  **"BATCH SCORING" (Streaming UI)**: `scoreSignals` fires an `onChunkScored` callback upon every chunk resolution.
3.  **State Insertion Logic**:
    ```typescript
    setLeads(prev => {
        const map = new Map(prev.map(l => [l.url, l]));
        chunkLeads.forEach(l => map.set(l.url, l));
        return Array.from(map.values()).sort((a, b) => b.score - a.score);
    });
    ```
    This React `setState` loop paints cards dynamically sorting by maximum `score` while the network is still processing the 50 remaining links.

### 6.2 Post-Process UI Masking (`displayedLeads`)
Job Cards are governed by client-side filtering variables: `filterUrgent`, `filterSalary`, `filterRecency`, `minScore`. **Toggling these variables DOES NOT re-trigger APIs.** They operate purely as a `.filter()` function on the `baseLeads` array before rendering the DOM. If filters return length 0, a custom Empty State counts the suppressed variables.

### 6.3 Supporting Dashboards 
*   **Outreach & Cover Letters**: Generates tailored emails comparing User Bio against Job Skills. `lib/ai.ts` routes these.
*   **`ApplicationBoard.tsx` (Kanban)**: Renders cards filtered by their `status` property. Dragging to a new column writes physically back into `LocalStorage` `jobradar_lead_score_cache`.
*   **`AnalyticsDashboard.tsx`**: Ingests all leads from the cache to draw D3/Recharts data distributions of geographic heatmaps and skill gaps.

## 7. Known Architectural Edge Cases / Directives for Cursor

If you are Cursor AI attempting to rebuild or augment this codebase, adhere to these constraints:
1.  **RAM Volatility (The Bloat Risk)**: Every scanned job retains a raw, un-compressed HTML `snippet` string in the React state. Do not map `.snippet` into `textarea` tags without truncating to 1500 chars to avoid render lag.
2.  **API Keys Exposed**: Keys sit in `LocalStorage`. They must be passed natively to fetch requests. Do not attempt to route them through an Express backend unless specifically tasked to rebuild the architecture from client-side to server-side.
3.  **Serper Object Limitations**: Google A/B tests its SERP DOM constantly. Serper JSON returns often mangle descriptions. Rely *heavily* on `cleanSnippet()` heuristic tuning rather than expecting clean JSON text. 
4.  **React Strict Mode Double-Fire**: In dev mode (`npm run dev`), React 18 will double-fire `useEffect`. You must rely heavily on `useRef` tokens to prevent dual-launching the `searchForSignals` sequence on mount.
